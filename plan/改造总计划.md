## 三、第 0 批：立即修复（阻断后续一切，最先做）

### 0-1 修复 ChatModel 注入歧义【P0】

**现象**：8 个全上下文测试报错（contextLoads、LoveAppDocumentLoaderTest、KnowledgeRepositoryTest×6），根因栈：

```
Error creating bean 'toolUseLoopRuntime': 构造器参数 0:
No qualifying bean of type 'ChatModel' available:
expected single matching bean but found 2: dashscopeChatModel, ollamaChatModel
```

**分析**：
- 上次会话新增 `common/config/ChatModelConfig.java`，声明 `@Bean @Primary fallbackChatModel`（dashscope 主 / ollama 备）。但报错只列 2 个候选 bean 而非 3 个 → 该配置在失败上下文中未生效，怀疑 `target/` 陈旧编译产物（**待验证**：`target/classes/com/sxw/sxwaiagent/common/config/ChatModelConfig.class` 是否存在）
- 直接原因：`ToolUseLoopRuntime` 构造器参数名为 `chatModel`；其余注入点（LoveApp / AiController / LegacyReActRuntime / QueryRewriter 等）参数名均为 `dashscopeChatModel`，靠 Spring 参数名匹配躲过歧义
- 回归嫌疑：`f595b2d fix: resolve ChatModel injection ambiguity with @Qualifier` 曾给 ToolUseLoopRuntime 和 HermesAgent 加 `@Qualifier("dashscopeChatModel")`，上次会话大改把 qualifier 弄丢了

**改法（双保险）**：
1. `ToolUseLoopRuntime` 构造器显式限定：`@Qualifier("dashscopeChatModel") ChatModel chatModel`
   （若希望 runtime 具备主备降级能力，改 `@Qualifier("fallbackChatModel")` —— 先定设计意图）
2. 检查 `HermesAgent` 的 ChatModel 注入是否同样丢了 qualifier（f595b2d 同时改过它）
3. 明确 `ChatModelConfig.fallbackChatModel` 定位：当前所有注入点按名字直连 dashscope，这个 @Primary bean 实际无人注入 → 要么 runtime 改用 fallback，要么删除该配置，避免误导

**验收**：`mvn clean test -Dskip.frontend=true` 相关 8 个错误消失。

## 四、第 1 批：P0 缺陷修复与闭环（上半）

### P0-1 修复健康检查路径失效（生产探针当前不工作）

- 根因：`server.servlet.context-path=/api/v1` 不影响 Actuator（`application.yml` 确认 `management.endpoints.web.base-path=/actuator`），真实端点为 `/actuator/health/liveness|readiness`，而探针请求的是不存在的 `/api/health`
- 修改：
  - `Dockerfile:32` → `wget -qO- http://127.0.0.1:${SERVER_PORT}/actuator/health/liveness`（liveness 不含依赖检查，避免 Redis 抖动误杀）
  - `docker-compose.yml:30` → readiness 探针 `/actuator/health/readiness`
  - 抽取 `HEALTHCHECK_PATH` 环境变量两处共用
- 验收：`docker compose up` 后 `docker inspect` 健康状态为 healthy

### P0-2 修复 LegacyReActRuntime 吞异常

- 现状：`LegacyReActRuntime` catch 一切返回通用话术，无法区分超时/限流/熔断
- 修改：
  - 新增 `agent/dto/AgentErrorKind.java` 枚举：`TIMEOUT / RATE_LIMIT / CIRCUIT_OPEN / MODEL_ERROR / UNKNOWN`
  - `AgentResponse` 增加可空 `errorKind` 字段（builder 追加，向后兼容）
  - catch 块按异常类型分类映射，差异化话术 + 分级日志
- 验收：mock 超时异常，断言 `errorKind=TIMEOUT` 且话术非通用文案

### P0-3 补全工具链 Validator / Hook 扩展点

- 现状：自述链路宣称 Validator/Hook，实际 `ToolExecutor` 未落地
- 新增（均在 `agent/tool/` 包）：
  - `ToolValidator` 接口 + 三个实现：`SchemaValidator`（按 inputSchema 校验必填/类型）、`SizeLimitValidator`（参数上限 `sxw.tool.validation.max-argument-chars` 默认 8192）、`InjectionGuardValidator`（`$(`、反引号、`../`、内网 IP，仅对高风险工具生效）
  - `ToolHook` 接口 + 两个实现：`MetricsHook`（Micrometer `tool.execution` Timer/Counter）、`ResultTruncationHook`（结果截断）
  - `ToolExecutor` 构造函数聚合注入 `List<ToolValidator>` / `List<ToolHook>`（空 List 兼容），执行序列：Registry → **validators**（失败即拒绝 + 审计 `validation_failed`）→ Risk → Approval → **hooks.before** → call → **hooks.after**（截断后入审计）→ Audit
  - 总开关 `sxw.tool.validation.enabled`（默认 true）
- 验收：缺必填参数调用被拦且审计落 `validation_failed`；超长结果被截断；Micrometer 存在 `tool.execution` 指标

## 五、第 2 批：P0 缺陷修复与闭环（下半）

### P0-4 修正工具结果消息协议（buildToolMessages 空实现）

- 现状：`ToolUseLoopRuntime.buildToolMessages` 返回空 List，工具结果仅靠 SystemMessage 注入，偏离标准 tool_result 协议
- 修改：
  - 循环内维护 assistant(tool_calls) + ToolResponseMessage 消息对，`buildToolMessages` 返回该列表
  - 新增开关 `sxw.agent.runtime.tool-message-protocol`：`system`（现状，默认）/ `standard`，灰度验证后切换默认值；standard 模式下关闭 SystemMessage 的 TOOL_RESULTS section 避免双重注入
  - 流式路径 `doExecuteStream` 同步修改
- 验收：standard 模式第二轮请求含 AssistantMessage(toolCalls)+ToolResponseMessage；多轮工具调用回归通过
- 风险：DashScope 对 tool role 兼容性取决于 Spring AI Alibaba 版本，故默认保持 system 模式

### P0-5 闭合 Hermes 复盘闭环（最大改造项）

- 现状：`HermesAnalyzer` 仅关键词启发式；`HermesApplier` 六个 apply 全 TODO；事件链 chatId 恒 null；`hermes/AgentRunCompletedEvent` 为无发布者的死代码且与 `agent/dto/AgentRunCompletedEvent` 重名
- 修改步骤：
  1. **事件修复**：`agent/dto/AgentRunCompletedEvent` 增加 `chatId`、`userMessage`（保留旧构造器委托兼容）；`ToolUseLoopRuntime` 三处发布点传入真实值；删除死代码 `hermes/AgentRunCompletedEvent.java`
  2. **Analyzer 接 LLM**：注入 ChatModel，system Prompt 限定输出 schema（type∈MEMORY/KNOWLEDGE/EVAL_CASE/AGENT_RULE、confidence∈[0,1]、最多 3 条、纯 JSON），confidence≥`sxw.hermes.min-confidence`（0.6）才入库；LLM 异常/超时（10s）/解析失败时回退现有启发式；开关 `sxw.hermes.llm-enabled`
  3. **Applier 落地**：
     - KNOWLEDGE → `DocumentIngestService.ingest(...)`（内容哈希去重保证幂等）
     - EVAL_CASE → `EvalService.createCase(...)`（要求 metadata 含 inputPrompt/expectedOutput，缺失拒绝并记录）
     - AGENT_RULE → 暂落地为 `MemoryRepository.save`（FEEDBACK 类型，标题前缀 `[RULE]`，可检索注入 Prompt），后续迁移独立 rule 表
     - PROMPT/TOOL/DOC 三类 → 写入 candidate metadata 并返回明确"已记录建议"文案，不再谎称 applied
  4. **失败补偿**：`HermesCandidateService.approveCandidate` 现状吞异常；新增 `APPLY_FAILED` 状态便于重试
- 验收：单测 mock ChatModel 断言生成候选；集成测试 approve KNOWLEDGE 候选后知识库可查；kill LLM 断言回退启发式不抛异常
